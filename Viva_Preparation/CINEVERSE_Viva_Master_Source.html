    5. Relational Schema and Data Types

    Score: 8.5 / 10 What is Implemented: Explicit data typing utilizing appropriate relational primitives:
  • Monetary values: DECIMAL(10,2) for zero round-off error
  • Time tracking: TIME for start/end, DATE for show date, TIMESTAMP with CURRENT_TIMESTAMP for audit logging
  • Text fields: Bounded VARCHAR(100) to VARCHAR(150); no unbounded TEXT fields
  • Numerical counts: INT with capacity > 0 and duration > 0
    • Evidence:
  • Verified via INFORMATION_SCHEMA.COLUMNS across all 15 tables.
    •  Design Strengths: Zero use of floating-point types (FLOAT or DOUBLE) for financial data, preventing binary floating-point rounding anomalies during revenue aggregation. Potential Weaknesses: Movie ratings use DECIMAL(3,1) allowing values up to 99.9 if unchecked, though constrained to $\le 10.0$ by check constraint chk_movie_rating. Examiner Challenge: "Why use DECIMAL(10,2) instead of FLOAT or DOUBLE for ticket prices?"
  • Defense: FLOAT and DOUBLE use IEEE 754 binary floating-point representation, which cannot precisely represent fractional decimal powers (e.g., $0.10$). In financial ledgers, accumulating rounding discrepancies violates accounting standards. DECIMAL stores numbers as fixed-point exact integers.
    • Concrete Improvement: Standardize currency ISO codes by adding a currency_code CHAR(3) DEFAULT 'INR' column to THEATER.

    6. Primary and Foreign Keys

     Score: 9.5 / 10 What is Implemented: Every table possesses a declared Primary Key. All 15 foreign key constraints are enforced by the InnoDB engine with explicit constraint names. Evidence:
  • Verified via INFORMATION_SCHEMA.KEY_COLUMN_USAGE
  • Composite Primary Keys:
    • BOOKED_SEAT: PRIMARY KEY (booking_id, seat_id) SNACK_ORDER_ITEM: PRIMARY KEY (snack_order_id, snack_id)
  • Composite Unique Constraints:
    • SCREEN: UNIQUE KEY uq_theater_screen (theater_id, screen_number) SEAT: UNIQUE KEY uq_screen_seat (screen_id, seat_number) Design Strengths: Composite unique keys prevent real-world duplication: Screen 1 cannot exist twice within the same theater; Seat A1 cannot exist twice within the same auditorium screen. Potential Weaknesses: None found. Primary and foreign key architecture is exemplary. Examiner Challenge: "What is the difference between a Primary Key and a Unique Constraint?"
  • Defense: A table can have only one Primary Key, which strictly forbids NULL values. A table can possess multiple UNIQUE constraints. In CINEVERSE, seat_id is the surrogate PK, while (screen_id, seat_number) is an alternate/candidate key enforced via a UNIQUE constraint.
    •  Concrete Improvement: None required.

    7. Relationship Cardinalities

    Score: 9.0 / 10 What is Implemented:
  • One-to-One (1:1): CUSTOMER ↔ ACCOUNT (enforced by UNIQUE (customer_id) on ACCOUNT), CUSTOMER ↔ LOYALTY_ACCOUNT (enforced by UNIQUE (customer_id) on LOYALTY_ACCOUNT), BOOKING ↔ PAYMENT (enforced by UNIQUE (booking_id) on PAYMENT).
  • One-to-Many (1:N): THEATER → SCREEN, SCREEN → SEAT, MOVIE → SHOWTIME, SCREEN → SHOWTIME, CUSTOMER → BOOKING, SHOWTIME → BOOKING, BOOKING → SNACK_ORDER.
  • Many-to-Many (M:N): BOOKING ↔ SEAT (via BOOKED_SEAT), SNACK_ORDER ↔ SNACK (via SNACK_ORDER_ITEM).
    • Evidence:
  • Live constraint definitions inspected in INFORMATION_SCHEMA.STATISTICS and KEY_COLUMN_USAGE.
    •  Design Strengths: Realizes 1:1 relationships using unique foreign keys rather than merging attributes into a bloated mega-table, preserving separation of concerns (patron demographics vs salted password credentials). Potential Weaknesses: None. Cardinalities faithfully mirror the business rules of cinema multiplex operations. Examiner Challenge: "Why is the relationship between BOOKING and SEAT Many-to-Many if a seat can only be booked once for a showtime?"
  • Defense: A physical seat (e.g., Seat 101) can be booked across hundreds of different showtimes over the year. Simultaneously, a single booking reservation can encompass multiple seats (e.g., a family booking 4 seats). Therefore, the relationship between the BOOKING entity and the physical SEAT entity is Many-to-Many ($M:N$), necessitating the BOOKED_SEAT junction table.
    • Concrete Improvement: None required.

    8. Normalization and Functional Dependencies

     Score: 8.5 / 10 What is Implemented: The schema satisfies 1NF, 2NF, and 3NF across all 15 tables. Evidence:
  • 1NF: All attributes are atomic (no comma-separated seats or array types).
  • 2NF: In tables with composite keys (BOOKED_SEAT and SNACK_ORDER_ITEM), non-key attributes (ticket_price, quantity, unit_price) depend on the entire composite key, not a proper subset.
  • 3NF: No non-key attribute is transitively dependent on the primary key via another non-key attribute. For example, SCREEN contains theater_id, while theater address and city remain strictly in THEATER.
    • Design Strengths: High structural integrity. Modifying a theater's street address requires updating exactly one row in THEATER, eliminating update anomalies across screens and showtimes. Potential Weaknesses: Controlled denormalization: BOOKED_SEAT stores ticket_price at the moment of reservation. This is an intentional historical financial snapshot, not an unnormalized redundancy anomaly. Examiner Challenge: "Does BOOKED_SEAT.ticket_price violate 3NF since base price is already stored in SHOWTIME?"
  • Defense: No. In transactional accounting, recording the executed ticket price is mandatory. If ticket base prices in SHOWTIME or tier multipliers change in the future, historical accounting records must reflect the exact price paid by the customer at the time of purchase. Storing this value preserves immutable financial history.
    •  Concrete Improvement: Formally document this design decision in the project report as intentional temporal snapshot denormalization.

    12. Transaction Management and Concurrency

     Score: 8.0 / 10 What is Implemented: Multi-statement ACID transactions implemented via conn.beginTransaction(), conn.commit(), and conn.rollback() in bookingController.js and showtimeController.js. Evidence:
  • backend/src/controllers/bookingController.js (Lines 154–351: createBooking)
  • backend/src/controllers/bookingController.js (Lines 363–407: cancelBooking)
    • Design Strengths: Atomicity is strictly respected. If snack inventory deduction fails after seat reservation, or payment fails, the entire transaction rolls back completely, leaving zero orphan rows. Potential Weaknesses: Concurrency race condition on seat selection! Step 5 of createBooking queries BOOKED_SEAT without an explicit row lock (FOR UPDATE) or serializable isolation. Two simultaneous requests checking the same seat could both see it as available before either commits. Examiner Challenge: "What happens if two users click 'Confirm Booking' for the exact same seat at the exact same millisecond?"
  • Defense (Honest & Defensible): In the current implementation, because the seat conflict query in Step 5 does not execute SELECT ... FOR UPDATE, and MySQL's default isolation level is REPEATABLE READ, both transactions could pass the conflict check and attempt insertion. While the application checks conflicts, under high concurrency a race condition is theoretically possible. To make this 100% concurrency-proof at the database engine level, we must either add FOR UPDATE to the seat validation query, or enforce an engine-level unique key constraint on (show_id, seat_id).
    •  Concrete Improvement: Add FOR UPDATE to the seat conflict check query or create a reservation lock table.

    13. Backend Database Driver and Integration

    Score: 8.5 / 10 What is Implemented: Connection pooling implemented via mysql2/promise with configuration parameters loaded from environment variables (.env). Evidence:
  • backend/src/config/db.js
  • Connection Pool Config: connectionLimit: 10, queueLimit: 0, waitForConnections: true, enableKeepAlive: true.
    •  Design Strengths: Asynchronous non-blocking I/O using native ES6 async/await. Connection pooling prevents socket exhaustion under bursts of HTTP requests. Potential Weaknesses: Connection pool size is fixed at 10; could be tuned dynamically based on production CPU cores. Examiner Challenge: "Why use connection pooling instead of opening a new mysql.createConnection() for each incoming HTTP request?"
  • Defense: Establishing a new TCP handshake and MySQL authentication session takes 20–50ms per request. Under 100 concurrent requests, creating individual connections exhausts server sockets and crashes MySQL. A connection pool keeps a pool of authenticated, ready-to-use connections alive, drastically reducing query latency to sub-2ms.
    • Concrete Improvement: Implement pool health monitoring and alert logging if queue wait time exceeds 200ms.

    Q1. What is CINEVERSE, and what primary problem does it solve?

    Spoken Answer: "Because cinema ticketing exhibits classic transactional relational challenges: Many-to-Many relationships between bookings and physical seats, strict scheduling constraints to prevent auditorium overlap, inventory control for concessions, and the absolute requirement for ACID transactions to prevent double-booking and financial discrepancies."

    Section C: ER Diagram & Relational Model

    Q21. What is an Entity in an ER diagram? Give examples from CINEVERSE.

    Spoken Answer: "An entity is a real-world object or concept that has an independent existence and about which data is stored. In CINEVERSE, MOVIE, THEATER, CUSTOMER, and SNACK are strong entities."

    Q22. What is the difference between an Entity and an Attribute?

    Spoken Answer: "An entity is the distinct object itself (e.g., MOVIE), whereas an attribute is a characteristic or property that describes that entity (e.g., title, duration, genre, rating)."

    Q23. What are Strong and Weak Entities? Are there any weak entities in your schema?

    Spoken Answer: "THEATER and MOVIE are strong entities because they have independent primary keys. SCREEN and SEAT exhibit existence dependency—a screen cannot exist without a theater, and a seat cannot exist without an auditorium screen. However, because we assign surrogate primary keys (screen_id, seat_id), they are implemented as regular relational tables with foreign keys and composite unique constraints."

    Q24. What is a Composite Key? Where is it used in CINEVERSE?

    Spoken Answer: "A composite key is a primary key that consists of two or more columns combined to uniquely identify a record. In CINEVERSE:
  • BOOKED_SEAT uses PRIMARY KEY (booking_id, seat_id).
  • SNACK_ORDER_ITEM uses PRIMARY KEY (snack_order_id, snack_id)."

    • Q25. What is a Candidate Key? Give an example from your tables.

    Spoken Answer: "A candidate key is any minimal set of attributes that can uniquely identify a tuple in a relation. In our CUSTOMER table, both customer_id and email are candidate keys. We selected customer_id as the Primary Key and enforced email as an alternate key using a UNIQUE constraint."

    Q26. What is a Surrogate Key versus a Natural Key?

    Spoken Answer: "A natural key is an attribute that exists inherently in the real-world domain, like a customer's email or a movie title. A surrogate key is an artificially generated identifier, such as an AUTO_INCREMENT INT (movie_id, booking_id). We use surrogate keys for faster integer index joins and to isolate the database from real-world data changes."

    Q27. What is a Junction Table (Associative Entity), and why is it necessary?

    Spoken Answer: "A junction table maps a Many-to-Many relationship between two tables into two One-to-Many relationships. Relational databases cannot directly implement M:N relationships without creating repeating groups or multi-valued columns. BOOKED_SEAT is our junction table connecting BOOKING and SEAT."

    Q28. How did you map the 1:1 relationship between CUSTOMER and ACCOUNT?

    Spoken Answer: "We placed customer_id as a foreign key inside the ACCOUNT table and applied a UNIQUE constraint (uq_account_customer). This guarantees that each customer can have at most one login account, enforcing strict 1:1 cardinality."

    Q29. How is the 1:1 relationship between BOOKING and PAYMENT enforced?

    Spoken Answer: "In the PAYMENT table, booking_id is defined with a UNIQUE constraint (uq_payment_booking) and references BOOKING(booking_id). This ensures that each booking ticket can have exactly one financial settlement record."

    Q30. Explain the cardinality between THEATER and SCREEN.

    Spoken Answer: "It is a One-to-Many ($1:N$) relationship. One theater complex contains multiple screens ($1 \dots N$), but each screen belongs to exactly one physical theater complex ($1:1$). The foreign key theater_id resides in SCREEN."

    Q31. Explain the cardinality between SCREEN and SHOWTIME.

    Spoken Answer: "It is One-to-Many ($1:N$). An auditorium screen hosts many showtimes over time ($1 \dots N$), but each specific screening event occurs in exactly one auditorium ($1:1$). The foreign key screen_id resides in SHOWTIME."

    Q32. Explain the cardinality between MOVIE and SHOWTIME.

    Spoken Answer: "It is One-to-Many ($1:N$). One movie title can be scheduled across multiple showtimes in various screens and dates, but each scheduled showtime features exactly one movie. The foreign key movie_id resides in SHOWTIME."

    Q33. What does Crow's Foot notation represent in your ER diagram?

    Spoken Answer: "Crow's Foot notation visually denotes relationship cardinality. A single vertical line represents 'one', a circle represents 'zero' (optionality), and a three-pronged fork (crow's foot) represents 'many'. For example, the line from SCREEN to SEAT ends with a crow's foot, representing that one screen has many seats."

    Q34. What is Referential Integrity?

    Spoken Answer: "Referential integrity is a database rule ensuring that a foreign key value in one table must always match an existing primary key value in the referenced table, or be null. It prevents invalid pointers and orphan records."

    Q35. What is an Orphan Record, and how does your database prevent them?

    Spoken Answer: "An orphan record is a child row whose foreign key references a parent row that no longer exists (for example, a showtime referencing a deleted movie). CINEVERSE prevents orphans using ON DELETE RESTRICT on critical relationships like SHOWTIME -> MOVIE and BOOKING -> CUSTOMER."

    Section D: Normalization & Functional Dependencies

    Q36. What is Normalization, and what is its primary objective?

    Spoken Answer: "Normalization is a systematic technique for organizing relational database tables to minimize data redundancy and eliminate update, insertion, and deletion anomalies while preserving data dependencies and lossless joins."

    Q37. What is First Normal Form (1NF)? Does CINEVERSE satisfy 1NF?

    Spoken Answer: "A relation is in 1NF if every attribute contains only atomic (indivisible) values, each column has a unique name, and there are no repeating groups. CINEVERSE satisfies 1NF because seats are never stored as comma-separated strings inside BOOKING; each seat is stored as an individual row in BOOKED_SEAT."

    Q38. What is a Functional Dependency? Give an example from your project.

    Spoken Answer: "A functional dependency $X \rightarrow Y$ means that the value of attribute $X$ uniquely determines the value of attribute $Y$. In our CUSTOMER table, customer_id $\rightarrow$ (customer_name, phone, email). Knowing the customer_id uniquely identifies the customer's name, phone, and email."

    Q39. What is Second Normal Form (2NF)?

    Spoken Answer: "A relation is in 2NF if it is in 1NF and no non-prime attribute is partially dependent on any candidate key. That is, every non-key attribute must depend on the     entire primary key, not a subset."

    Q40. Demonstrate how CINEVERSE satisfies 2NF using BOOKED_SEAT.

    Spoken Answer: "BOOKED_SEAT has a composite primary key: (booking_id, seat_id). Its non-key attribute is ticket_price. The ticket_price depends on     both the booking instance and the specific physical seat tier. It does not depend solely on booking_id or seat_id alone. Therefore, there are no partial dependencies, satisfying 2NF."

    Q41. Demonstrate how SNACK_ORDER_ITEM satisfies 2NF.

    Spoken Answer: "SNACK_ORDER_ITEM has a composite primary key: (snack_order_id, snack_id). Non-key attributes are quantity and unit_price. Both attributes describe the line item and depend on both the specific order and the specific snack. Hence, it is fully in 2NF."

    Q42. What is Third Normal Form (3NF)?

    Spoken Answer: "A relation is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on the primary key via another non-prime attribute ($X \rightarrow Y$ and $Y \rightarrow Z$ where $Z$ is non-key)."

    Q43. Demonstrate how CINEVERSE satisfies 3NF using the SCREEN and THEATER tables.

    Spoken Answer: "In SCREEN, the attributes are screen_id, screen_number, screen_name, screen_type, capacity, and theater_id. Notice that theater details—such as theater_name, city, and address—are     not stored in SCREEN. If they were, we would have screen_id $\rightarrow$ theater_id and theater_id $\rightarrow$ city, a transitive dependency. By isolating theater attributes in THEATER, we eliminate transitive dependencies and satisfy 3NF."

    Q44. What is Boyce-Codd Normal Form (BCNF)?

    Spoken Answer: "BCNF is a stricter version of 3NF. A relation is in BCNF if, for every non-trivial functional dependency $X \rightarrow Y$, the determinant $X$ is a superkey. All of our tables with single-column surrogate primary keys naturally satisfy BCNF."

    Q45. What is an Insertion Anomaly? Give an example of how your design prevents it.

    Spoken Answer: "An insertion anomaly occurs when certain attributes cannot be inserted without the presence of other unrelated attributes. For example, if movies and showtimes were merged into one table, you could not insert an upcoming movie into the catalog until a showtime was scheduled. Our design separates MOVIE from SHOWTIME, allowing us to add movies with zero scheduled showtimes."

    Q46. What is a Deletion Anomaly?

    Spoken Answer: "A deletion anomaly occurs when deleting one piece of data unintentionally removes unrelated data. If theaters and screens were combined, deleting the last screen in a venue would accidentally delete the entire theater's address and record. In CINEVERSE, deleting a screen preserves the THEATER record."

    Q47. What is an Update Anomaly?

    Spoken Answer: "An update anomaly occurs when data redundancy forces the same value to be updated in multiple rows, risking data inconsistency. If theater addresses were duplicated across every showtime row, changing an address would require updating thousands of records. In 3NF, the address exists in exactly one row in THEATER."

    Q48. Is there any intentional Denormalization in CINEVERSE?

    Spoken Answer: "Yes, in BOOKED_SEAT.ticket_price. While the base price originates in SHOWTIME, recording ticket_price in BOOKED_SEAT represents an immutable financial snapshot at the time of purchase. If ticket base prices change tomorrow, past booking revenues remain historically accurate."

    Q49. What is a Lossless Join Decomposition?

    Spoken Answer: "A decomposition of relation $R$ into $R_1$ and $R_2$ is lossless if joining $R_1$ and $R_2$ on their common attribute yields the exact original relation $R$ without generating spurious tuples. In our schema, $R_1 \cap R_2$ always forms a superkey for at least one relation, guaranteeing lossless joins."

    Q50. What is Dependency Preservation?

    Spoken Answer: "Dependency preservation means that all functional dependencies of the original relation can be enforced simply by checking the constraints on the individual decomposed tables, without needing to perform a join. Our schema preserves all dependencies."

    Section E: SQL, MySQL Engine & Relational Theory

    Q51. What are the five major categories of SQL commands?

    Spoken Answer: "1. DDL (Data Definition Language): CREATE, ALTER, DROP, RENAME, TRUNCATE.
  • DML (Data Manipulation Language): INSERT, UPDATE, DELETE.
  • DQL (Data Query Language): SELECT.
  • DCL (Data Control Language): GRANT, REVOKE.
  • TCL (Transaction Control Language): COMMIT, ROLLBACK, SAVEPOINT."

    • Q52. What is the difference between TRUNCATE and DELETE?

    Spoken Answer: "DELETE is a DML command that removes rows one by one, logs individual row deletions in the transaction log, fires delete triggers, and can be rolled back. TRUNCATE is a DDL command that deallocates the table's data pages, resets auto-increment counters, is faster, and cannot be rolled back in some configurations."

    Q53. What is an INNER JOIN versus a LEFT OUTER JOIN?

    Spoken Answer: "An INNER JOIN returns only rows that have matching values in both tables. A LEFT JOIN returns all rows from the left table, and the matched rows from the right table; if no match exists, NULL values are returned for the right table's columns. In CINEVERSE, we use LEFT JOIN BOOKING when querying all customers so that customers with zero bookings are still included."

    Q54. What are Aggregate Functions in SQL? Name the five core functions.

    Spoken Answer: "Aggregate functions perform a calculation on a set of rows and return a single summary value. The five core functions are: COUNT(), SUM(), AVG(), MIN(), and MAX(). In reportController.js, we use SUM(total_amount) to compute gross theater revenue."

    Q55. What is the difference between WHERE and HAVING clauses?

    Spoken Answer: "WHERE filters individual rows     before any grouping or aggregation takes place. HAVING filters aggregated groups after the GROUP BY clause has been evaluated. For example, WHERE booking_status = 'CONFIRMED' GROUP BY movie_id HAVING COUNT() > 5."

    Q56. What are the ACID properties in database transactions?

    Spoken Answer: "- Atomicity: All statements in the transaction succeed, or the entire transaction is rolled back ('all or nothing').
  • Consistency: The database transitions from one valid state to another, satisfying all schema constraints.
  • Isolation: Concurrent transactions execute without interfering with one another.
  • Durability: Once committed, changes are permanently written to non-volatile storage and survive power failures."

    • Q57. How are ACID properties maintained during CINEVERSE ticket booking?

    Spoken Answer: "In createBooking, we execute await conn.beginTransaction(). If seat validation, customer check, seat insertion, payment simulation, or snack deduction fails, await conn.rollback() is triggered. Changes are only made permanent when await conn.commit() executes."

    Q58. What is a Clustered Index versus a Secondary (Non-Clustered) Index in MySQL InnoDB?

    Spoken Answer: "In InnoDB, the primary key forms the Clustered Index, meaning table rows are physically stored on disk in the B+ Tree order of the primary key. A Secondary Index stores the index column and points to the clustered index primary key. When querying by secondary index, InnoDB looks up the secondary index first, then traverses the clustered index (index lookup)."

    Q59. What secondary indexes exist in your CINEVERSE database?

    Spoken Answer: "Our foreign keys and search columns have secondary B-Tree indexes:
  • idx_showtime_date on SHOWTIME(show_date)
  • idx_showtime_movie on SHOWTIME(movie_id)
  • idx_showtime_screen on SHOWTIME(screen_id)
  • idx_booking_customer on BOOKING(customer_id)
  • idx_booking_showtime on BOOKING(show_id)
  • idx_booking_status on BOOKING(booking_status)"

    • Q60. What is a Subquery? What is the difference between a Correlated and Non-Correlated subquery?

    Spoken Answer: "A subquery is a SELECT query nested inside another query. A non-correlated subquery executes once independently, and its result is used by the outer query. A correlated subquery references columns from the outer query and must be evaluated repeatedly for each row processed by the outer query."

    Q61. What does the COALESCE() function do?

    Spoken Answer: "COALESCE() accepts a list of arguments and returns the first non-NULL value. In our revenue reporting queries, we write COALESCE(SUM(b.total_amount), 0.00) so that if a movie has zero confirmed bookings, the query returns 0.00 instead of NULL."

    Spoken Answer: "
    
CREATE PROCEDURE sp_get_movie_revenue(IN p_movie_id INT, OUT p_revenue DECIMAL(10,2))
BEGIN
    SELECT COALESCE(SUM(b.total_amount), 0.00) INTO p_revenue
    FROM BOOKING b

    "

    Section G: Movie, Theatre & Showtime Management

    Q76. How does the system prevent an auditorium from being double-booked for two movies at the same time?

    Spoken Answer: "When an admin attempts to schedule a screening, adminCreateShowtime checks the database for any existing showtime on that screen and date where $(s_{start} < end_{calc} \land s_{end} > start_{form})$. If a conflict is found, the server rejects the request with HTTP 409 Conflict and names the conflicting movie and time slot."

    Q77. Can a movie exist in the database without any showtimes?

    Spoken Answer: "Yes. In our relational schema, SHOWTIME holds the foreign key movie_id referencing MOVIE. MOVIE does not hold a foreign key to SHOWTIME. Thus, movies can be inserted into the catalog months ahead of release."

    Q78. Can a showtime exist without a movie or screen?

    Spoken Answer: "No. In SHOWTIME, both movie_id and screen_id are defined as INT NOT NULL foreign keys. The MySQL engine will reject any showtime insertion where either identifier is null or references a non-existent row."

    Q79. What happens if an admin tries to delete a movie that already has scheduled showtimes?

    Spoken Answer: "The operation is rejected. First, the backend controller checks SELECT show_id FROM SHOWTIME WHERE movie_id = ? and returns HTTP 409. Second, at the database level, fk_showtime_movie enforces ON DELETE RESTRICT, throwing MySQL Error 1451."

    Q80. How is auditorium screen seating configured?

    Spoken Answer: "Screens have capacity ranging from 112 to 160 seats. Physical rows are assigned letters (A through K), and numbers (1 to 16). Rows A–D are Standard, E–H are Premium, and I–K are VIP/Recliner. The unique constraint uq_screen_seat (screen_id, seat_number) prevents duplicate seat labels in the same auditorium."

    Q81. How does the customer website discover which movies are playing in a specific city?

    Spoken Answer: "The customer frontend queries GET /api/theaters. When the user selects a city (e.g., 'Bengaluru'), the UI filters showtimes by joining THEATER on city = 'Bengaluru', displaying only screenings occurring in multiplexes within that metropolitan area."

    Q91. What is the purpose of the FOR UPDATE clause in SQL?

    Spoken Answer: "SELECT ... FOR UPDATE acquires an exclusive row-level lock on the read rows within an InnoDB transaction. Any other concurrent transaction attempting to read or update those locked rows is blocked until the first transaction commits or rolls back. In CINEVERSE, we use FOR UPDATE on SNACK inventory and BOOKING cancellation."

    Q92. What are the four ANSI SQL Transaction Isolation Levels?

    Spoken Answer: "1. Read Uncommitted: Permitted dirty reads.
  • Read Committed: Prevents dirty reads; non-repeatable reads possible.
  • Repeatable Read: (MySQL InnoDB default) Prevents dirty and non-repeatable reads; phantom reads mitigated by Next-Key Locking.
  • Serializable: Highest isolation; fully serializes access using range locks."

    • Q93. What is a Dirty Read, Non-Repeatable Read, and Phantom Read?

    Spoken Answer: "- Dirty Read: A transaction reads uncommitted changes made by another transaction that might later be rolled back.
  • Non-Repeatable Read: A transaction reads the same row twice and observes different data because another transaction committed an update in between.
  • Phantom Read: A transaction re-executes a query returning a range of rows and finds new 'phantom' rows inserted and committed by another transaction."

    1. What is the database name?

    MovieTheaterDB.

    2. What storage engine does MySQL use, and why?

    InnoDB, because it supports ACID transactions, foreign keys, and row-level locking.

    3. How many tables are in your database?

    Exactly 15 base tables.

    4. Name the two junction tables in your schema.

    BOOKED_SEAT (resolves Booking ↔ Seat) and SNACK_ORDER_ITEM (resolves Snack Order ↔ Snack).

    5. What are the composite primary keys in your project?

    BOOKED_SEAT(booking_id, seat_id) and SNACK_ORDER_ITEM(snack_order_id, snack_id).

    6. What normal form does the database satisfy?

    Third Normal Form (3NF) across all tables, with single-attribute PK tables satisfying BCNF.

    7. Why isn't seat availability a boolean column in the SEAT table?

    Because a physical seat is available or booked relative to a specific showtime, not permanently.

    8. How is live seat availability calculated?

    Available Seats = Total Screen Seats $-$ Booked Seats for that specific show_id in BOOKED_SEAT.

    9. What is the mathematical condition for scheduling conflict detection?

    $A_{start} < B_{end} \land A_{end} > B_{start}$ on the same screen and date.

    10. How much turnaround buffer is added between movie screenings?

    15 minutes (turnaroundMins = 15), automatically calculated in showtimeController.js.

    11. What happens if an admin tries to delete a movie with active showtimes?

    MySQL blocks the deletion with an Error 1451 foreign key constraint violation (ON DELETE RESTRICT).

    12. What happens to child seats if a screen is deleted?

    All physical seats belonging to that screen are automatically cascade-deleted (ON DELETE CASCADE).

    13. What data type is used for financial amounts?

    DECIMAL(10,2) to prevent binary floating-point roundoff errors.

    14. What data type is used for movie ratings?

    DECIMAL(3,1) constrained between 0.0 and 10.0 via check constraint chk_movie_rating.

    15. How many check constraints are active in your database?

    22 active CHECK constraints.

    16. What happens when a booking is cancelled?

    BOOKING.booking_status is updated to 'CANCELLED' and PAYMENT.payment_status is set to 'REFUNDED'.

    17. Why aren't rows deleted from BOOKED_SEAT upon cancellation?

    To preserve historical transaction audit trails while immediately releasing seat availability relationally.

    18. How do you prevent SQL injection in your Node.js backend?

    By strictly using parameterized queries (? placeholders) executed via pool.execute().

    19. What is a 1:1 relationship in your schema? Give two examples.

    No; validations and transaction boundaries are handled in Express controllers for portability and testability.

    WHERE filters individual rows before grouping; HAVING filters aggregated groups after GROUP BY.

    Read Uncommitted, Read Committed, Repeatable Read (MySQL default), and Serializable.

    Acquires exclusive row-level locks on read rows, blocking concurrent transactions until commit or rollback.
